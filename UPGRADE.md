# Обновление Selectel Hunter

## Что изменилось

Сохранены конфигурации ru-1, ru-3 и ru-9. Добавлена Москва ru-2 с API
`https://ru-2.cloud.api.selcloud.ru/network/v2.0` и постоянной внешней сетью
`8cc4ee6a-8dc9-4865-8877-ef5b5cdef020`. Все три московские подсети используют
эту сеть. UUID подсети передаётся отдельно в `subnet_id`.
Создание IP не запрашивает API для определения UUID сети. Кнопка обновления
подсетей обращается только к `floatingip_pools`; сохранённые варианты остаются
доступными при ошибке обновления. Для импорта диапазона API должен вернуть
`cidr` и `subnet_id` (или `id`). Неизвестные форматы не интерпретируются как сеть.

Выбор: «Начать поиск» → аккаунт → Москва / Санкт-Петербург
→ подсети. Каждая подсеть создаёт отдельное задание. Повторное нажатие запуска
возвращает существующее задание; завершённые задания повторно не выделяют IP.
Регионы существующих заданий не переписываются. Глобальные
переключатели регионов и подсетей сохранены как общие ограничения выполнения.
«Мои задания» показывает состояния `pending`, `running`, `paused`, `completed`,
`failed`, `cancelled`, попытки, ошибки, результат и время с момента создания.
Пауза аккаунта останавливает новые запросы всех его заданий; пауза задания
действует только на выбранную подсеть. Уже отправленный запрос может завершиться,
и его результат всё равно сохраняется.

## Причины ненадёжности прежней реализации

- Запущенные обработчики учитывались только в словаре процесса. Блокировки
  `asyncio.Lock` не защищали от второго процесса и не позволяли вернуть
  зависшую работу в очередь.
- `start_pair` игнорировал подсеть, а выбор подсетей менял глобальные настройки.
  Аккаунт мог начать проверять диапазоны, выбранные для другого аккаунта.
- Счётчик попыток сбрасывался с новым BURST. Незавершённая операция выделения
  не сохранялась, и после таймаута следующий круг мог выделить второй IP.
- Результат, история и выключение цели сохранялись разными транзакциями.
  Ошибки доставки Telegram только записывались в лог, уведомление терялось.
- Не были настроены WAL, резервная копия перед миграцией, ротация файлов логов,
  межпроцессная блокировка и проверка дискового пространства.

## Гарантии и границы восстановления

`queue_jobs` хранит владельца, аккаунт, регион, CIDR/UUID, состояние, даты,
счётчики, ошибку, расписание следующей попытки, lease, метку операции,
внешнюю сеть, промежуточный ресурс и результат. Получение задания выполняется
под `BEGIN IMMEDIATE`; изменения обработчика требуют действующего lease token.
Lease продлевается каждые 10 секунд на 60 секунд. Независимый watchdog каждые
15 секунд освобождает истёкшие lease. Сохраняются паузы, отмены и метки операций.
Попытка ограничена 180 секундами, включая ожидание API; после отмены запроса
следующий цикл может выполнить новый POST. Число фоновых обработчиков ограничено
числом активных аккаунтов, завершённые задачи удаляются из памяти.

Перед POST транзакционно записывается уникальная метка, передаваемая в
`description`. После потери ответа или 5xx повторный POST выполняется в следующем
обычном слоте. При потерянном успешном ответе возможно выделение лишнего IP.
Когда ответ получен, результат, история, статистика и outbox сохраняются одной
транзакцией. Неподходящий IP удаляется только после повторного GET и проверки
ID, метки, проекта, сети и отсутствия привязки к порту. Чужие ресурсы сохраняются.
Поля ресурса соответствуют [Neutron Networking API](https://docs.openstack.org/api-ref/network/v2/).

Если после неоднозначного ответа ресурс не найден, отсутствие в списке ещё
не доказывает, что запрос не завершится позже. Задание остаётся на сверке
каждые 5 минут и показывает ошибку `Outcome of allocation is unresolved`.
Автоматически очищать `operation_id` в такой ситуации нельзя. Нужно проверить
операцию и ресурсы в Selectel; простое «Продолжить» сохраняет метку и выполняет
сверку. Это ограничение внешнего API без подтверждённого ключа идемпотентности.
При отсутствии обязательных полей владения бот сохраняет ресурс и сообщает
об ошибке вместо предположений о его принадлежности.

Ошибки 401 после одного перевыпуска токена, 403, некорректный запрос/404 и
исчерпание квоты переводят задание в `failed`: исправьте причину и нажмите
«Продолжить». 409 без признаков квоты означает отсутствие свободных IP.
429 сохраняет паузу аккаунта не короче `Retry-After`. Временные ошибки
используют backoff с jitter, задания не сбрасываются. Токен обновляется перед
истечением срока либо один раз после 401. Все операции явно выбирают регион;
неизвестный регион отвергается без запроса.

Уведомления о найденных IP и ошибках доставляются отдельным outbox-циклом.
Повторяющиеся ошибки одного типа объединяются, учитываются настройки уведомлений
и Telegram Retry-After. Недоступность Telegram не блокирует обработчики поиска.
Доставка имеет семантику «как минимум один раз»: если процесс упадёт между
отправкой Telegram и записью подтверждения, возможно повторное уведомление,
но повторного выделения IP из-за этого не происходит.

## Обновление сервера с systemd

1. Остановите старый процесс: `sudo systemctl stop selectel-ip-hunter`.
   Убедитесь, что нет вручную запущенных старых обработчиков.
2. Сделайте внешнюю резервную копию каталога проекта, `.env`, текущего кода и БД.
   После остановки процесса копируйте также `-wal`/`-shm`, если они остались.
   Сохраните прежний `ENCRYPTION_KEY`: новый ключ не расшифрует старые пароли.
3. Обновите файлы кода без замены `.env` и `selectel_hunter.db`.
4. В каталоге `/opt/selectel-ip-hunter` установите зависимости:
   `venv/bin/python -m pip install -r requirements.txt`.
5. Новые переменные из `.env.example` необязательны: интервал запросов,
   connect/read timeouts, файл логов, health-файл и порог свободного места.
   Для ru-2 переменная сети не нужна: UUID задан в `app/config/regions.py`.
6. Проверьте права записи в каталог БД, `logs/` и каталог health-файла.
   SQLite следует хранить на локальном диске сервера, не на сетевом ресурсе.
7. Установите обновлённый unit и запустите:

   ```bash
   sudo cp selectel-ip-hunter.service /etc/systemd/system/
   sudo systemctl daemon-reload
   sudo systemctl enable --now selectel-ip-hunter
   sudo journalctl -u selectel-ip-hunter -n 100 --no-pager
   ```

8. Миграция выполняется при запуске. Перед изменением старой схемы SQLite
   backup API создаёт `selectel_hunter.db.before-v3-<UTC timestamp>.bak`.
   Старые аккаунты, ID, настройки, таблицы истории и результатов не удаляются.
   Повторные запуски не создают новые задания для тех же целей.
9. Откройте «Мои задания». Старые незавершённые задания без меток операций,
   а также аккаунты с прерванным BURST импортируются на паузе: сначала проверьте
   уже выделенные IP в Selectel, затем продолжите нужные задания. Это необходимо,
   потому что прежний код не сохранял исходы отправленных запросов.
   Новая Москва не добавляется в старые задания автоматически.
10. Проверьте `venv/bin/python -m app.healthcheck`. Код 0 означает свежий
    watchdog, работающий scheduler и достаточное место на диске; 1 — проблему.
    Проверка локальная и не создаёт ресурсов. Подключите команду к мониторингу.

systemd автоматически запускает бот после перезагрузки и перезапускает после
падения. На одну БД допускается один процесс бота: ОС удерживает файл `.lock`
до завершения процесса. Сам файл удалять не нужно. Независимо от этой блокировки
очередь защищает каждое задание атомарным claim и lease. Для ручного запуска
также используйте `python -m app.main`.

Логи ротируются по 5 MiB, сохраняются пять архивов. Health-файл обновляется
каждые 15 секунд; свободное место проверяется для диска БД. При низком остатке
healthcheck возвращает ошибку и в журнале появляется сообщение. История попыток
в БД сохраняется: размер БД и свободное место следует отслеживать мониторингом.

Откат: остановите новый процесс; сохраните отдельно его БД с новыми результатами;
верните старый код и согласованную резервную копию БД. Не подменяйте БД у
работающего процесса и не удаляйте новые результаты без сверки ресурсов Selectel.

## Проверка изменений

```bash
venv/bin/python -m compileall -q app tests
venv/bin/python -m pytest -q -p no:cacheprovider
```

Новые тесты используют временные SQLite-файлы и моки Selectel/Telegram.
Предыдущий этап модернизации: 87 пройденных тестов. Проверки интерфейса описаны ниже.
Покрыты оба региона, независимые задания, конкурентный claim, потеря процесса
и lease, устаревший обработчик, пауза/отмена, timeout после POST, восстановление
без второго POST, 7+ дней неоднозначных ответов с виртуальным временем, 429,
истекающий токен, временный сбой, недоступность Telegram, проверка владения
перед удалением, фиксированная сеть ru-2, обновление подсетей, старая схема,
резервная копия и повторные миграции. Длительная реальная работа и доступ к
боевому Selectel не проверялись; многодневные сбои моделируются тестами.

## Интерфейс Telegram, версия схемы 3

Города в интерфейсе соответствуют следующей группировке:

| Город | Конкретные регионы заданий | Внешняя сеть |
| --- | --- | --- |
| Москва | ru-2 | `8cc4ee6a-8dc9-4865-8877-ef5b5cdef020` |
| Санкт-Петербург | Все ключи `REGIONS`, кроме ru-2; сейчас ru-1, ru-3, ru-9 | Прежняя сеть каждого региона |

Группировка Петербурга следует конфигурации, а не заменяет регион задания на
условный `spb`. API по-прежнему выбирается по конкретному `job.region`.
Переключение города меняет только предпочтение пользователя для нового поиска.
Регионы, подсети, UUID, lease и результаты существующих заданий не меняются.
Одновременно можно иметь московские и петербургские задания на одном аккаунте.
Обычный запуск переключает выбранные аккаунты на новый набор подсетей, а
остальные их активные задания ставит на паузу. Для добавления заданий без паузы
существующих используется «Добавить параллельно». Одна подсеть соответствует
одному заданию и одной находке.

Главное меню, выбор города, задания, статистика и история используют общий
стиль с HTML-экранированием. Активные задания находятся в начале списка.
Остановка требует отдельного подтверждения. Числовые кнопки старых задач
открывают актуальную карточку или архив, не останавливая весь аккаунт.
Неизвестные, удалённые и устаревшие кнопки предлагают открыть `/start`.
Доступ к карточкам и ресурсам проверяется по владельцу даже при переходе из
уведомления в теме супергруппы.

Команды `/start`, `/status`, `/stats`, `/help`, `/cancel` доступны после
перезапуска; меню команд регистрируется через Telegram API. Ошибки подключения
polling вызывают переподключение, а не завершение поиска. SIGINT/SIGTERM
останавливают polling, живые карточки и фоновые обработчики штатно; исход
неоднозначного запроса сохраняется прежним механизмом очереди.

### Дополнительные данные без замены очереди

Миграция с версии 2 на 3 создаёт только таблицы представления и наблюдений:

- `user_preferences`: город, фиксированное смещение UTC, период карточки;
- `job_ui_states`: время попытки, успешной операции, явной паузы, продолжительность
  включённого состояния и признак непрерывного сбоя;
- `job_operations`: время начала каждой новой операции выделения, без повторов
  от heartbeat или сверки после таймаута;
- `resource_observations`: последний статус ресурса, явно проверенный через GET;
- `subnet_drafts`: выбор подсетей, аккаунт и город для конкретного набора кнопок;
- `notification_cooldowns`: время успешной доставки объединяемого уведомления.

Таблицы `queue_jobs`, `hunter_tasks`, `found_ips`, `notification_outbox` и
алгоритм получения/продления lease сохранены. Наблюдения и события записываются
в транзакции соответствующего изменения. События отправляются через прежний
`notification_outbox`; второго механизма отправки нет.

Перед миграцией версии 2 создаётся резервная копия `.before-v3-*.bak`.
Повторный запуск версии 3 не сбрасывает задания и не создаёт новые копии без
изменения версии схемы. Старые архивы `.before-v2-*.bak` остаются пригодными
для отката к соответствующему коду. Рабочую БД при установке не заменяйте.

### Реальные показатели и часовой пояс

Карточка показывает счётчики своего задания, его конкретный регион и подсеть.
Позиция ожидания относится к последовательной очереди его аккаунта; другие
аккаунты работают независимо. Пауза всего аккаунта показывается отдельно от
паузы одного задания, со ссылкой на управление аккаунтом.

Время поиска — календарное время включённого задания за вычетом зарегистрированных
явных пауз; это не время HTTP-запросов и не uptime процесса. Суммарное время
складывается по заданиям, в том числе параллельным. Если до обновления начало
или паузы не регистрировались, интерфейс показывает «Нет данных».

Общие попытки — сохранённые счётчики заданий. Почасовые показатели и скорость
считаются по новым `job_operations` и отражают наблюдения с обновления; старые
промежутки не заполняются вымышленными значениями. Ошибки API считаются по
журналу; штатное отсутствие свободных IP не считается ошибкой API. Ответ 409
подтверждает восстановление доступности API, но не записывается как успешная
операция выделения. История находок включает также сохранённые старые результаты.

Часовой пояс хранится как смещение UTC в минутах, по умолчанию UTC+05:00.
В настройках доступны UTC+00:00, UTC+03:00 и UTC+05:00. Задания, уведомления,
расписание, статистика и история используют это смещение. Автоматического
перехода на летнее время у фиксированного смещения нет.

### Живые карточки и уведомления

`UI_REFRESH_SECONDS=20` задаёт начальный период для новых пользователей.
Кнопки настроек предлагают 15, 20 и 30 секунд; валидный диапазон 15–300 секунд.
Пользовательское значение сохраняется в БД. Один независимый цикл обновляет
существующие сообщения; отдельные задачи на каждую карточку не создаются.
Неизменившийся текст и клавиатура не отправляются повторно. Навигация и фоновое
редактирование одного сообщения сериализованы, поэтому позднее обновление не
перекрывает новое меню. FloodWait учитывается, удалённые/недоступные сообщения
отписываются. Общий бюджет — не более одного изменённого сообщения в секунду;
при большом числе пользователей фактический интервал может быть больше выбранного.

Одновременно хранится одна живая карточка на пользователя и не более 200 всего.
Подписка действует до навигации или 24 часов; нажатие «Обновить» включает её
снова, в том числе после рестарта. До 20 последних черновиков выбора подсетей
на пользователя хранятся в БД, старше 30 дней удаляются. Их кнопки не зависят
от памяти FSM и сохраняют привязку к аккаунту и городу. Выбор подсетей разбит
на страницы, callback_data проверяются тестами на лимит Telegram 64 байта.

Находки имеют приоритет в существующем outbox и проверяются к отправке раз в
секунду. Отдельное сообщение содержит регион, подсеть, IP, время, счётчик и
кнопки «Информация об IP» / «Открыть задание». Заявление о сохранении выводится
только при наличии подтверждённого результата в БД. История разбита на страницы.
Текущий статус ресурса не предполагается: для проверки используется отдельная
кнопка GET в правильном регионе; статус хранится с датой проверки. Эта кнопка
не создаёт, не удаляет и не изменяет IP.

Запуск, пауза, возобновление, остановка и восстановление после рестарта попадают
в тот же outbox. Устаревшие сообщения о текущем состоянии объединяются; отдельные
находки не объединяются. При непрерывном сбое отправляется одно уведомление по
заданию и одно о восстановлении. Общий cooldown для одинаковых ошибок на
подсетях одного аккаунта и региона сохраняется в БД и использует настройку
объединения уведомлений. Неудачная отправка не активирует cooldown и остаётся
в outbox. Telegram Retry-After и backoff доставки сохранены.

Обычный рестарт не создаёт повторных уведомлений о находках: подтверждение
доставки остаётся в БД. Прежняя граница «как минимум один раз» сохраняется:
авария между принятием сообщения Telegram и записью подтверждения может дать
повтор. У Bot API нет общей транзакции с SQLite; скрывать эту границу как
гарантию абсолютного exactly-once было бы неверно. Правила Bot API:
[inline-кнопки, HTML и редактирование сообщений](https://core.telegram.org/bots/api).

### Журнал запросов IP

Обработчик постоянной очереди пишет INFO-записи `selectel_request` в stderr
(для systemd — journal) и в ротируемый `LOG_FILE`, по умолчанию `logs/hunter.log`
относительно рабочего каталога службы. Для каждой попытки видны начало и исход:
аккаунт, ID задания, регион, CIDR/UUID подсети, номер попытки, действие
`allocate`/`reconcile`, результат, известный HTTP-код, время и задержка повтора.
Неизвестный HTTP-код отображается как `—`, успешный код не придумывается.
При находке после фиксации в БД появляется `selectel_found` с IP и UUID ресурса.
Секреты и текст исключений API в эти записи не включаются. Нужен `LOG_LEVEL=INFO`
или `DEBUG`; при `WARNING` штатные запросы не видны.

После обновления `app/hunter/durable.py` именно в каталоге, указанном в unit:

```bash
systemctl show selectel-ip-hunter -p WorkingDirectory -p ExecStart
systemctl restart selectel-ip-hunter
journalctl -u selectel-ip-hunter -f -o cat | grep --line-buffered 'selectel_'
```

Пауза, выключенная цель и ожидание следующего цикла не означают отправку POST;
при отсутствии реальных попыток записей `selectel_request` не будет. Доставка
Telegram и логирование запросов — независимые действия.

После добавления журнала запросов: **127 тестов прошли**, включая четыре новые
проверки контекста, HTTP-ошибок, отсутствия секретов и сверки без повторного POST.
`compileall` и `git diff --check` — без ошибок.

### Исправление запуска выбранного города

Ранее `selected_region` менял предпочтение в меню, но обработчик «Запустить все»
не передавал его планировщику. Старые петербургские задания продолжали работу;
у новых аккаунтов цели выбирались по прежнему `account.region`, часто ru-3.
Строка «Регион: Москва» при этом не означала, что активны московские задания.

Теперь:

- «Запустить выбранный город» берёт сохранённый выбор и для всех аккаунтов
  владельца создаёт/возобновляет цели только этого города. Для Москвы это три
  подсети ru-2. Остальные активные задания этих аккаунтов ставятся на паузу.
- Выбор подсетей одного аккаунта работает аналогично: обычный запуск оставляет
  активным только выбранный набор. Другие аккаунты не затрагиваются.
- «Добавить параллельно» сохраняет работу других городов и подсетей.
- Первый запуск пустого аккаунта также использует выбранный город, а не старое
  поле региона аккаунта. Простое возобновление уже существующей очереди аккаунта
  сохраняет её регионы; для переключения используйте запуск выбранного города.
- Главный экран разделяет «Выбор для запуска» и фактически активные задания
  Москвы/Петербурга. «Мои задания» по умолчанию показывает выбранный город;
  вкладки позволяют открыть другой город или все сохранённые задания.
- Переключение сохраняется транзакционно: регион, ID, счётчики, найденные IP,
  lease и метка незавершённой операции не сбрасываются. Изменяется только статус
  неподходящих активных заданий на `paused`. Задания других владельцев не меняются.
- Проверка статуса в транзакции начала операции запрещает новый POST от задания,
  поставленного на паузу между проверкой в обработчике и фиксацией операции.
  Уже отправленный POST может завершиться; найденный IP будет сохранён в прежнем
  регионе. При неизвестном исходе следующий запуск выполняет новую попытку.
- Если выбранный город или подсети выключены, запуск не сообщает об успехе и
  сохраняет работающие задания. Дополнительной миграции схемы не требуется.

Для сервера обновите проект целиком: изменены `app/db/queue.py`, `ui.py`,
`app/hunter/account_manager.py`, `app/bot/scheduler_ui.py`, `multisubnet.py`,
`experience.py`, `screens.py`, `jobs.py`, `keyboards.py`, `views.py`.
Не заменяйте `.env` и SQLite-файлы. Затем перезапустите службу и откройте:
`/start` → «Выбрать регион» → «Москва» → «Запустить выбранный город».
Один выбор города без нажатия запуска не изменяет работающие задания;
это явно отображается в интерфейсе. После запуска новые `selectel_request`
для выбранных аккаунтов должны иметь `region=ru-2` (кроме завершения уже
отправленных до переключения запросов).

После исправления запуска города: **138 тестов прошли** (11 новых проверок),
`compileall`, импорт приложения, синтаксис Python 3.11 и `git diff --check` —

### Повторы без увеличения задержки

NO_FREE_IP, сетевые сбои, 5xx и 429 используют следующий обычный слот BURST.
Число попыток, история ошибок и заголовок Selectel `Retry-After` не увеличивают
задержку. Растущий backoff и случайный jitter удалены из обработки ошибок.
Ответ 429 не включает дополнительный cooldown аккаунта и не мешает обходить
остальные подсети. Настроенные период BURST и интервал между запросами сохраняются.

В HTTP-клиенте повторные GET/HEAD/DELETE после 429 и 5xx используют обычный
`API_REQUEST_INTERVAL`. Переподключение после сетевого сбоя использует постоянную
паузу 0,15 с на каждой попытке. Число локальных попыток ограничено, после чего
ошибка возвращается в очередь. После потерянного ответа POST следующая попытка
создания выполняется в обычный слот без блокирующей сверки `UNRESOLVED`.
Если Selectel уже создал IP, но ответ потерялся, повтор может выделить ещё один IP.

`retry_seconds` в журнале показывает время до следующего слота задания,
поэтому оно зависит от момента завершения запроса, но не от числа ошибок.
БД и ранее сохранённые сроки ожидания автоматически не переписываются.
Чтобы снять старую задержку задания, приостановите его и возобновите через бота.
Настройки регионов, сохранённые намерения операций и защита устойчивой очереди
не меняются.

### Самопроизвольные остановки после ошибок API

Ошибки Selectel, включая 400/401/403/404 и квоту, больше не переводят задание
в `failed` и не блокируют весь аккаунт. Ошибка остаётся в карточке и уведомлениях;
следующая попытка выполняется в обычном слоте. Ошибки проверки принадлежности
ресурса по-прежнему требуют вмешательства: чужие и подключённые IP не удаляются.

При запуске сервиса старые задания `failed` с сохранённой ошибкой вида
`<тип ошибки>: HTTP <код>` автоматически возвращаются в очередь активных аккаунтов.
Ручные паузы/остановки, завершённые задания, остановленные аккаунты и намерения
операций сохраняются. Очередь и БД не пересоздаются.

Период `T` из настроек сохраняется. Для `N` активных аккаунтов шаг запусков — `T / N`:
при 90 секундах и 20 аккаунтах это 4,5 секунды. Аккаунты выполняют запросы независимо;
следующий старт своего аккаунта считается от запланированного начала цикла.
Если цикл длится дольше периода, тот же аккаунт не запускается параллельно самому
себе; остальные продолжают по расписанию.

Новые строки `selectel_schedule` показывают действующие `active_accounts`,
`period_seconds`, `stagger_seconds`. Строки `selectel_burst` показывают число
попыток создания, сверок и состояния заданий каждого аккаунта за цикл.
Блокирующая сверка `UNRESOLVED` удалена. Старое намерение без полученного ресурса
заменяется новым при следующем запуске задания; запись истории операции остаётся.
В журнале это `selectel_intent_replaced`, затем обычный `action=allocate`.
Заданный период не меняется, дополнительные паузы и backoff не добавляются.
Для IP с уже сохранённым ответом сохраняются завершение обработки и проверка
принадлежности перед удалением; чужие и подключённые IP не удаляются.

Проверено: 153 теста общей серии и отдельный новый тест трёх кругов по 20 аккаунтов
с шагом `T / N`; все прошли. Дополнительно проверены 60 попыток по трём подсетям
на 20 аккаунтах после ошибок API и восстановление старых автоматических остановок.

После удаления блокировки UNRESOLVED: 154 теста общей серии и две отдельные
проверки восстановления уже полученного ответа; все прошли. Старые намерения,
таймауты и 5xx больше не блокируют последующие запланированные POST.

### Только уведомления о правах и квотах

Автоматическая отправка разрешена только для `PERMISSION_ERROR` и
`QUOTA_EXCEEDED`. Уведомления о восстановлении, авторизации, сетевых сбоях,
5xx, 429, отсутствии IP, запуске/паузе/остановке, перезапуске и найденных IP,
а также автоматические отчёты выключены. Найденные IP сохраняются и доступны
в истории бота; статистика доступна по запросу через меню.

Уже накопленные отключённые уведомления подтверждаются в outbox без отправки
и больше не повторяются. Защита разрешённых уведомлений от повторов, настройки
доставки и повтор после сбоя Telegram сохраняются. Частота запросов Selectel
и очередь заданий не меняются.
